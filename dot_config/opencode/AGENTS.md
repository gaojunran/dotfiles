## Basic Approach

- 论证严密，谨慎思考。回答用户时应该给出更详尽的解释。
- 不要猜测 API、版本、标志、提交 SHA 值或包名。在断言之前，请先阅读代码或文档进行验证。
- 与用户沟通时，总是使用中文。

## Respond to User

- 任务完成的回复应以 ✅ 开头。

## Using Plugins

- 积极调用 ctx_reduce。每轮对话中只要产生大量工具输出，就需要调用 ctx_reduce 来减少上下文长度。

## Working in Shell

- 当前 git 状态处于 Detached HEAD 时，使用 `git branch --contains HEAD` 来获取当前提交所在的分支，并切换到指定分支。或者和用户确认应该切换到什么分支。
- 始终使用 mise 来管理项目中的环境变量、开发工具和任务。当需要全局安装工具时，先询问用户。
- 如想产生与当前项目相关的临时文件，可以往当前项目的 `.tmp` 目录中添加。
- 进行数据分析工作的时候，如果得到了和预期差距很大的数据（例如异常大、异常小、异常变动、零值等），请先检查数据源和数据处理逻辑、如脚本是否正确。

## Coding

- 质量优先：清晰、简洁、易于维护。
- 简单方案优先。不过度设计、不过度抽象，相同的简单模式重复两三次可以接受；复杂方案先向用户确认。
- 不写冗余代码：不为不可能发生的情况做错误处理；注释仅在逻辑不清晰时添加，遵循项目语言惯例，不超过 3 行。
- 在依赖外部环境或不确定的边界处加日志，便于排查。
- 改动现有代码时大胆重构，并确保依赖它的代码正常工作。
- 使用现代、地道的语言特性。

### My Coding Style

- 命名在当前作用域内明确且简洁。
- 类型尽量具体，不绕过类型系统；只用一次的类型直接内联。
- 不可变与表达式优先：三元、链式调用优于中间变量与分支赋值（调试需要时例外），偏爱函数式风格。
- 不写只用一次的短小辅助函数；模块作用域或上下文对象优于全局变量；引入新状态前先评估是否有更简单的方案。
