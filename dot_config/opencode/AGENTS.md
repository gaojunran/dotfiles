## Basic Approach

- 论证严密，谨慎思考。回答用户时应该给出非常详尽的解释、假定用户是小白用户。
- 不要猜测 API、版本、标志、提交 SHA 值或包名。在断言之前，请先阅读代码或文档进行验证。
- 与用户沟通时，总是使用中文。
- Commit Message 始终使用英文。Issue/Discussion/Change Request/评论/评审的语言需要参考项目惯例。
- 当你要做的工作预估需要 30min 以上时，应该定期向用户汇报中间进度。

## Using Plugins

- 积极调用 ctx_reduce。每轮对话中只要产生大量工具输出，就需要调用 ctx_reduce 来减少上下文长度。
- 积极调用 ctx_expand。较久远的会话会被定期压缩，可能丢失一些细节。尤其是用户需要你做报告等需要精确回忆过去对话记录的时候，应该展开过去会话的具体内容。

## Working in Shell

- 禁止使用 Python 脚本 / bash 命令来修改代码。使用提供的专有工具更稳健、更具可观测性。
- 当前 git 状态处于 Detached HEAD 时，使用 `git branch --contains HEAD` 来获取当前提交所在的分支，并切换到指定分支。可切换分支不唯一时，和用户确认应该切换到什么分支。
- 始终使用 mise 来管理项目中的环境变量、开发工具和任务。当需要全局安装工具时，先询问用户。
- 如想产生与当前项目相关的临时文件，可以往当前项目的 `.tmp` 目录中添加。
- 进行数据分析工作的时候，如果得到了和预期差距很大的数据（例如异常大、异常小、异常变动、零值等），请先检查数据源和数据处理逻辑、如脚本是否正确。
- 避免使用 sleep。结果返回时间不确定时，尽量用有超时的轮询而不是等待特定时间。定期感知你工作的时间，发现流程中有异常耗时的部分应该想办法优化。
- 在做覆写操作（如 write 一个已存在的文件、调用 github 接口更新一个 PR 描述）的时候，应该先调用读接口确认该文件 / 资源没有变动，因为用户可能在你不知道的时候修改过这个文件。如果有改动，合并你的改动和用户的改动。
- 提交时使用白名单提交的方式，即只提交你预期内的代码文件和配置文件、资源文件等。有文档和其他预期之外的文件改动要提交前，先交由用户确认。

## Coding

- 质量优先：清晰、简洁、易于维护。
- 简单方案优先。不过度设计、不过度抽象，相同的简单模式重复两三次可以接受；复杂方案先向用户确认。
- 不写冗余代码：不为不可能发生的情况做错误处理；注释仅在逻辑不清晰时添加，遵循项目语言惯例，不超过 3 行。
- 在依赖外部环境或不确定的边界处加日志，便于排查。
- 改动现有代码时大胆重构，并确保依赖它的代码正常工作。
- 使用现代、地道的语言特性。
- 命名在当前作用域内明确且简洁。
- 类型尽量具体，不绕过类型系统；只用一次的类型直接内联。
- 不可变与表达式优先：三元、链式调用优于中间变量与分支赋值，偏爱函数式风格。
- 不写只用一次的短小辅助函数；模块作用域或上下文对象优于全局变量；引入新状态前先评估是否有更简单的方案。
- 【重要 必须】新需求第一次编写代码后，必须审查变更代码的正确性和简洁性。典型的问题是：这段代码是不是应该写在这里？是否有性能、可维护性问题？是否有更简单且功能上等价的写法？
- 【重要 必须】为现有代码新增功能后，需要审视变更代码附近的现有代码，看是否有可优化点可以让代码的简洁性和可维护性提升？可以提给用户，让用户决定是否顺手优化。
