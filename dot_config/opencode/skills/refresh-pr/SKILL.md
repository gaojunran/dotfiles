---

## 基本步骤

列出当前项目中用户的所有 open PR，不含 draft PR。批量查看其内容、评论、CI 状态、合并状态；批量查看它们关联的 Issue 的内容、状态和评论。

1. 对于有合并冲突的 PR 应解决冲突。
2. 对于 CI 失败的 PR 应确认失败原因。如果失败问题在主干而非我们新增的提交上，则无需处理，保持现状。如果是我们引入，则需处理。
3. 对于未处理的 bot 的评论意见（包含关联 Issue 中的），应自动化处理。如果处理的过程没有推送新代码（例如改描述等），需要推个空提交，因为一般 bot 都由推送事件刷新。
4. 对于未处理的人类的评论意见（包含关联 Issue 中的），应该和用户确认后再执行。

以上的处理应该尽量合并一次推送，不要分开推送以免重复触发多次 CI 或 Review。

处理完之后，报告用户你做了什么，是否有下一步需用户确认的事项。

## 特殊情况

1. 如果该 PR 的合并冲突源于这部分代码上游有更新，该功能**已被实现**或**现在已无法实现，如此功能被移除或变更等**，则需和用户确认是否要关掉此 PR。
2. 在处理以上四条的时候，如果引入了实现思路的变更/重构、和 Issue 或用户需求产生偏离的情况，应该和用户确认，并同步更新 Issue 和 PR 描述。
