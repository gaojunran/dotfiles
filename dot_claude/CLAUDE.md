## Basic Approach

- 写入文件前请先阅读现有文件。除非文件已更改，否则请勿重新读取。
- 论证严密，表达简洁。
- 不要猜测 API、版本、标志、提交 SHA 值或包名。在断言之前，请先阅读代码或文档进行验证。
- 不使用 Emoji 或破折号。
- 与用户沟通时，总是使用中文。代码注释的语言应该尊重现有项目的惯例。

## Working in Shell

- 稍显复杂的探索任务，请编写 JavaScript 脚本，用 Node 来执行。
- 总是使用 ripgrep `rg` 而不是 `grep`。前者是性能更好的片段查找工具。
- 总是使用 `fd` 而不是 `find`。前者是性能更好的文件查找工具。
- 在目的明确地检索代码时，偏爱 `ast-grep`。它是基于 AST  的代码搜索工具，可以帮助你更准确地找到相关代码片段。

## Coding

- 代码质量第一位 —— 代码应该清晰、简洁、易于理解和维护。
- 谨慎使用注释 —— 仅在逻辑不清晰时才使用。
- 多打日志 —— 在依赖外部环境、复杂逻辑或不确定的边界条件下，添加日志以帮助调试和理解代码行为。
- 不要进行过度设计 —— 通常应该选择简单的可行方案。但是应该让用户确认一些复杂的方案是否必要。
- 不要进行过度抽象 —— 相同、简单的模式重复两三次是可以接受的。
- 不要编写不可能存在的异常边界 —— 对于不可能发生的事情，不进行错误处理。切忌冗余的代码。
- 大胆重构 —— 当本次任务需要改动到现有代码时，大胆重构现有代码以适应新需求。但要确保依赖其的代码依然正常工作。
- 使用地道的语法 —— 使用现代的语法特性、符合当前编程语言习惯的写法。

### My Coding Style

- 变量命名：变量名需要在 **当前作用域内** 明确且具有描述性。以下是几个例子：
  - 在 `selection` 组件内部，不要编写一个名为 `selectionPrefixSum` 的变量。仅需 `prefixSum` 即可。
  - 在 lambda 函数中，变量名短是可以接受的。
  - 复杂的布尔条件组合，可以使用更长的变量名来提高可读性。例如 `isMultitaskGesture` 等。
- 提供明确的类型。
  - 尽量避免使用 `any`。积极在代码库中探索现有的、更具体的类型，并使用它们。如果一定要使用 `any`，请在注释中说明原因。
  - 新建文件优先使用 TypeScript，除非是小脚本等无需类型的情况。
  - 除非是要明确多次使用的类型，否则不需要依次提供接口或类型别名。内联类型是完全可以接受的。
- 不变优于可变。以下是几个例子：
  - 三元运算符优于 `if () { xxx = 1 } else { xxx = 2 }`。
  - 使用连续的方法调用，并接收其结果，比使用中间变量更好。（当然，如果用户有调试需求，则可以使用后者来方便调试）
  - 偏爱函数式编程。
