## Basic Approach

- 论证严密，表达简洁。
- 不要猜测 API、版本、标志、提交 SHA 值或包名。在断言之前，请先阅读代码或文档进行验证。
- 与用户沟通时，总是使用中文。代码注释的语言应该尊重现有项目的惯例。严禁产生长串的多行注释用来解释代码逻辑；如果必要，也应该把行数控制在 3 行以内。

## Using Plugins

- 积极调用 ctx_reduce。每轮对话中只要产生大量工具输出，就需要调用 ctx_reduce 来减少上下文长度。

## Working in Shell

- 当前 git 状态处于 Detached HEAD 时，使用 `git branch --contains HEAD` 来获取当前提交所在的分支，并切换到指定分支。或者和用户确认应该切换到什么分支。
- 始终使用 mise 来管理项目中的环境变量、开发工具和任务。当需要全局安装工具时，先询问用户。
- 如想产生与当前项目相关的临时文件，可以往当前项目的 `.tmp` 目录中添加。

## Coding

- 代码质量第一位 —— 代码应该清晰、简洁、易于理解和维护。
- 谨慎使用注释 —— 仅在逻辑不清晰时才使用。
- 多打日志 —— 在依赖外部环境、复杂逻辑或不确定的边界条件下，添加日志以帮助调试和理解代码行为。
- 不要进行过度设计 —— 通常应该选择简单的可行方案。但是应该让用户确认一些复杂的方案是否必要。
- 不要进行过度抽象 —— 相同、简单的模式重复两三次是可以接受的。
- 不要编写不可能存在的异常边界 —— 对于不可能发生的事情，不进行错误处理。切忌冗余的代码。
- 大胆重构 —— 当本次任务需要改动到现有代码时，大胆重构现有代码以适应新需求。但要确保依赖其的代码依然正常工作。
- 使用地道的语法 —— 使用现代的语法特性、符合当前编程语言习惯的写法。

### My Coding Style

- 变量命名：变量名需要在 **当前作用域内** 明确且具有描述性。保持变量名简洁且有意义。
- 提供明确的类型。
  - 尽量避免使用 `any`。积极在代码库中探索现有的、更具体的类型，并使用它们。如果一定要使用 `any`，请在注释中说明原因。
  - 新建文件优先使用 TypeScript，除非是小脚本等无需类型的情况。
  - 除非是要明确多次使用的类型，否则不需要依次提供接口或类型别名。内联类型是完全可以接受的。
- 不变优于可变。以下是几个例子：
  - 三元运算符优于 `if () { xxx = 1 } else { xxx = 2 }`。
  - 使用连续的方法调用，并接收其结果，比使用中间变量更好。（当然，如果用户有调试需求，则可以使用后者来方便调试）
  - 偏爱函数式编程。
- 工整地组织项目。以下是几个例子：
  - 不要编写函数体短小、且不被多次使用的函数。简单的模式重复两三次是可以接受的。
  - 权衡使用全局变量和局部变量。通常模块作用域变量、上下文对象等模式优于全局变量。
  - 避免状态泛滥。每次为了解决一个特殊情况引入新状态时，都先评估一下有没有更好的方案。
